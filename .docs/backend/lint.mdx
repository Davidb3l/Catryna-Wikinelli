# `catryna lint` — structural doc health

A different question from every other command in the suite, and the distinction is the point:

| Command | Question |
|---|---|
| `catryna drift` | Has the **code** outgrown this doc? |
| `catryna lint` | Is this **doc** structurally sound and honestly anchored? |

Drift can only speak about docs that anchor code, and only about whether that code moved. It says nothing about a doc whose frontmatter is unparseable, whose callout tags are orphaned, or whose anchors point at paths that were never there. Those docs render broken or silently document nothing — and until this shipped, nothing in the toolchain looked for them.

## Rules

Every rule was earned by a real failure in this repo, not invented.

| Rule | Severity | Why it exists |
|---|---|---|
| `frontmatter` | error | No parseable `---` block — the doc has no path, tags or baseline, so the index and the file disagree from then on |
| `unclosed-callout` | error | The lossy MDX round-trip's signature: an orphaned closing tag renders as literal text mid-document |
| `unclosed-fence` | error | A fence that is never closed swallows the rest of the doc into a code block |
| `empty-fence` | warning | Fence **balance** is not fence **content**. A doc can be structurally perfect and almost entirely hollow — headings and prose wrapped around blank boxes |
| `volatile-fact` | warning | A repo-wide number/version/date in prose has no anchor, so drift can never flag it when it rots. Nudges toward a computed token (CAT-2) |
| `missing-anchor` | error | An anchor to a path not on disk documents nothing. Drift calls this `broken` **only once a baseline exists**; lint catches it immediately |
| `windows-anchor` | error | A backslash path matches nothing off Windows, so the doc silently stops being drift-checked at all |
| `index-mismatch` | error (path) / warning (title) | `_index.json` and the frontmatter disagreeing means one of them is lying to whoever read it first |
| `orphan-file` | warning | A `.mdx` no index entry names is invisible to search, drift and coverage |
| `missing-file` | error | An index entry with no file behind it 404s in the viewer |

## The hollow-doc rule

`empty-fence` exists because balance and content are different questions, and only one of them was being asked. A real doc in a consuming corpus had 12 empty fences — including the ` ```mermaid ` block that was supposed to *be* the architecture diagram, and nine ` ```typescript ` blocks under headings like "Step 1: User Clicks Run Migrations". It rendered as headings and prose wrapped around blank boxes, it had been through a full repair pass reported clean throughout, and `catryna lint` called it well-formed. A human going looking is what found it.

`scanFences()` pairs fences the way CommonMark does, and **both** fence rules now read from it. That replaced `unclosed-fence`'s old "count ` ``` ` lines, flag an odd total" heuristic, which was wrong in both directions: a ` ```` ` block wrapping a ` ``` ` example has an even count and is fine, while ` ```ts ` followed by a ` ``` trailing-text ` line has an odd count but the second line does not actually close anything. The parity rule called the first malformed and the second fine — at **error** severity, so its false positives gated CI on legitimate docs.

Pairing rules that matter: a closing fence must use the same marker character, be at least as long as the opener, and carry nothing but whitespace after it; a backtick info string may not contain a backtick (so ` ```` ` wrapping an example opens one fence, not two); and `~~~` fences count, exactly as `stripCode` already assumed.

Three deliberate choices in the `empty-fence` rule itself:

- **Warning, not error.** An empty fence is legitimate in a template or a draft, and a gate that fails on it trains people to bypass the gate. It must still *surface* — silence is what let a hollow doc pass.
- **One issue per doc, not per fence.** The failure is a hollow document; a dozen blank blocks should read as one dozen-block problem, not flood the report. The message lists the first five lines and counts the rest.
- **A fence still open at EOF is not reported.** That is `unclosed-fence`'s finding, and naming one defect twice trains people to ignore the report.

Line numbers are file-relative (the frontmatter block is counted back in), so they can be jumped to directly.

## The unpoliceable-claim rule (`volatile-fact`)

Drift polices claims about **anchored files**. A repo-wide measurement written in prose — `6,600 lines`, `14 modules`, `28 tests`, a version, a date — spans the whole tree, so no anchor can fire on it and it rots **invisibly**. This is not hypothetical: Sirius Forester's `architecture/overview` claimed `6,600 lines across 14 modules` while the real count had drifted past it, and the doc verified clean the whole time. Author-time is the only moment the class is catchable, so it lives in lint, not drift.

`findVolatileFacts` scans prose line by line (fenced code and inline code stripped, since a number in code is data, not a claim) for two patterns: a number followed by a plural **count noun** (`lines`, `modules`, `files`, `tests`, `loc`), and a **dotted version** (`v1.3.0`, `version 1.3.0`). A **computed token** (below) is the correct form and is never flagged — the two rules teach the same habit from opposite sides.

<Callout type="warning">
Two of the originally-proposed triggers were **pulled back after calibrating against the real corpus** — the field test is ground truth, and this codebase's prime directive is that a validator which cries wolf gets ignored. **Percent** (`%`) was dropped: it fired almost entirely on algorithm constants ("rounds up to 100"), an idiom ("100% CPU"), and narrative bug examples ("33% live vs 100% trend"), none separable from the one claim that rots. **Dates** are cue-gated: a bare date in prose is usually historical and immutable (`the dogfood (2026-08-01)`), so only a date carrying a currency cue (`current as of <date>`) fires. Counts and dotted versions — the strong signal, and the exact rot the rule was filed about — survived unchanged.
</Callout>

## What it deliberately does NOT check

No prose opinions — no line length, no heading order, no spelling.

<Callout type="info">
A gate that fails on style trains people to bypass the gate. Every rule here describes a doc that is **broken**, not one that is merely unfashionable.
</Callout>

## The false-positive guard

`stripCode()` removes fenced blocks and inline code **before** looking for markup.

Without it the checker flags a doc that merely *mentions* a closing callout tag inside backticks. That is not hypothetical: it happened in this repo, to the ad-hoc shell checker this command replaces, on a doc describing that very failure mode.

<Callout type="warning">
A validator that cries wolf gets ignored, and an ignored validator is worse than none — it provides the feeling of coverage without the fact of it. The false-positive guard is the most important code in this module.
</Callout>

## Exit codes

Matches the `drift` convention exactly:

| Code | Meaning |
|---|---|
| `0` | No errors. Warnings may be present — **warnings never gate** |
| `3` | One or more errors: the gate is hit |
| `1` | Operational failure (unreadable `_index.json`) — distinct from the gate |

<Callout type="warning">
`--json` **always exits 0**, matching `drift --json`: a `--json` invocation is a REPORT whose consumers read the body (`ok`, `errors`), not the exit code. This shipped wrong. The Stop hook does `out=$(catryna lint --json) || out=""`, so the non-zero exit blanked the output in precisely the case worth reporting — the hook stayed silent on a malformed doc. Twenty-one green tests missed it because none asserted the `--json` exit code; it took a second consumer actually using the command to surface it.
</Callout>

Under `--json` there is exactly one object on stdout and stderr stays clean, per SUITE_CONTRACTS §4. Operational failure in human mode goes to stderr so stdout stays pipeline-safe.

## Interaction with `verify`

`catryna verify` refuses to record a baseline on a structurally malformed doc, checked **before** the write so a rejection leaves the previous baseline intact. `verify` is the chokepoint every doc passes through, so nothing structurally broken can ever claim to be verified.

<Callout type="warning">
The guard is scoped to `STRUCTURAL_RULES` — `frontmatter`, `unclosed-callout`, `unclosed-fence` — and deliberately **excludes anchor resolution**. A vanished anchor means the *code* moved, which is drift's question; `verifyDoc` already reports it as a `brokenAnchors` warning while still recording the baseline. Blocking there would overrule that decision and make re-verifying a doc after a rename impossible.
</Callout>

## Surfaces

- **CLI:** `catryna lint [--json]`
- **MCP:** `lint_docs` — in its own `src/tools/lint.ts`, not folded into the drift tools, because it is a different question with a different gate

## Design rules

Same two as `src/coverage.ts`, for the same reasons: `lintDocs(cwd)` takes its root as a **parameter** and never reads `process.cwd()`, and every issue carries an **actionable hint** rather than only a diagnosis — asserted by a test.
