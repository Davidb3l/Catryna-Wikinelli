# Frontend Application

The frontend is a React application built with Vite, providing a visual interface for humans to browse and view documentation created by Claude Code.

## Tech Stack

- **React 19** - UI framework

- **Vite 8** - Build tool and dev server (with `@vitejs/plugin-react` 6)

- **React Flow** (`reactflow` 11) - Architecture diagrams

- **Mermaid** - Text-based diagrams, themed from `initMermaid()` in `components/MermaidDiagram.tsx`

- **tldraw** - Whiteboard/canvas support

- **Tailwind CSS v4** — a real build step via `@tailwindcss/vite`, configured **CSS-first** in `index.css` (`@import "tailwindcss"` + an `@theme` block). It previously loaded `cdn.tailwindcss.com`, which compiled Tailwind *in the browser on every page load* and kept the whole design system in an inline `<script>`; the viewer now ships ~70 KB of purged CSS and no runtime compiler.

- **Lucide React** - Icon library

React Flow, Mermaid and tldraw are all **lazily loaded**; none of them is
reachable from the entry chunk. See *Bundle & code splitting* below before
importing any of them.

TypeScript types come from `@types/react` / `@types/react-dom`. They were missing entirely until Phase 2 review, which meant every React API was untyped — the real cause of the long-standing "11 pre-existing type errors". Adding them cost zero new errors and turned both error clusters out to be genuine typing bugs the absence had hidden (`NodeProps` parameterized by the node type instead of the data type; `querySelector` returning `Element` where `HTMLElement` was needed). The frontend typechecks clean at **0 errors**, and `bun run typecheck` makes that enforceable.

Dependencies are limited to what the viewer actually uses. `@tiptap/*` and `diff` were declared but dead (`@tiptap/*` never imported, `diff` imported by `App.tsx` and never called) and have been removed from `package.json`. The `index.html` importmap they were also listed in is gone entirely — see *Bundle & code splitting*.

## Bundle & code splitting

The three heavy libraries — `mermaid`, `reactflow`, `tldraw` — are **lazy**, and
that is load-bearing rather than an optimization detail. They were imported at
`App.tsx` module scope, so every page view paid for all three: a **1394 KiB**
entry chunk, of which mermaid was the bulk (it pulls in cytoscape, katex, and a
separate chunk per diagram type). Most docs open none of them.

Each library now sits behind **one boundary module**, reached through
`React.lazy` + `<LazyCanvas>`. The precise invariant is that no module in the
**eager import graph** — everything reachable from `index.tsx` by a non-`import
type`, non-`import()` edge — pulls in a heavy library. (`components/TurboNode.tsx`
and `TurboEdge.tsx` do import `reactflow`; they are fine because only
`FlowDiagram` reaches them, so they land in its lazy chunk.)

| Boundary module | Library | Fetched when |
|---|---|---|
| `components/MermaidDiagram.tsx` | `mermaid` (+ cytoscape, katex, per-type chunks) | a block has `metadata.diagramData.mermaid` |
| `components/FlowDiagram.tsx` | `reactflow` (+ the Turbo node/edge components) | the non-mermaid diagram branch, or the architecture editor |
| `components/WhiteboardCanvas.tsx` | `tldraw` | the whiteboard editor is opened (`activeEditor === 'wb'`) |

Measured on the built bundle: a doc with **no** diagram loads 2 JS chunks; a
mermaid doc and a React Flow doc each pull their own; tldraw arrives only when
the whiteboard modal opens.

**The CSS is split the same way.** `reactflow/dist/style.css` and
`tldraw/tldraw.css` are imported by their boundary modules, so Vite emits them
as chunk CSS loaded with the chunk. A cold page view fetches exactly one
stylesheet, `index.css`, and **makes no third-party request at all**.

<Callout type="warning">
Both used to be render-blocking `<link>`s in `index.html` pointing at **esm.sh**:
a third-party CDN round-trip before first paint, on every page view, for canvases
almost nobody opens. The tldraw one was pinned to `2.0.0-canary.c41d8e14798e`
while `package.json` installed 2.4.x, and that URL had begun returning **HTTP
500** — so the whiteboard rendered unstyled and the blocking request bought
nothing at all. Importing from `node_modules` removes the CDN, the version skew
(it now tracks `package.json` by construction) and the blocking cost together.

The `<script type="importmap">` that mapped `react`, `reactflow` and `tldraw` to
esm.sh went at the same time. Vite resolves bare specifiers at build, so it had
been inert — but it was inert *and* pinned to the same stale canary, which is
exactly the shape of thing someone later trusts.
</Callout>

<Callout type="warning">
**Vendor CSS must be imported through the `layer(vendor)` wrappers in
`frontend/styles/`, never directly.** Chunk CSS lands in the document *after*
`index.css`, and unlayered rules of equal specificity are decided by order — so
a plain `import 'reactflow/dist/style.css'` let reactflow's defaults beat this
project's Turbo overrides. `.react-flow__node-default { color: #222 }` won over
the themed light text and three nodes rendered as **empty dark rectangles**.

The layer alone is **not** sufficient, and it is worth being exact about why. A
layer's position is fixed by its **first declaration anywhere in the document**.
`vendor` was first declared in a chunk sheet injected after everything else, so
it landed *above* Tailwind's `utilities`: unlayered rules still won — the
hand-written half of `index.css` was fine — but every Tailwind utility the app
put on a reactflow or tldraw element quietly lost. Nothing broke only because
all of them happened to be `!`-prefixed.

`index.css` therefore opens with an explicit order:

```css
@layer properties, theme, base, vendor, components, utilities;
```

`vendor` above `base` (Tailwind's preflight lives there and would otherwise
strip tldraw's chrome), below `components`/`utilities` (so the app's own classes
win). Built output confirms `properties < theme < base < vendor < components <
utilities < unlayered`.

With that in place the `!`-prefixed utilities on reactflow's `<Controls>` and
`<MiniMap>` became redundant and are gone — a layered rule loses to `utilities`
on layer precedence alone, so specificity never enters into it. Verified
pixel-identical: controls at `left/bottom: 16px` on desktop and `8px` under
`sm:`, minimap `block` / `none` across the breakpoint. **If you find yourself
reaching for `!` against vendor CSS again, the layer order is wrong — fix that
instead.**
</Callout>

<Callout type="warning">
**Layering a vendor sheet cuts both ways: unlayered app CSS now outranks it too,
whatever the specificity.** Two global rules in `index.css` started reaching
into the tldraw canvas the moment its stylesheet moved into a layer — `*
{ -webkit-tap-highlight-color: … }` overrode tldraw's deliberate `transparent`
(an indigo flash on every tap in a drawing surface), and the mobile
`button { min-height: 44px }` touch-target floor inflated its 32px toolbar
buttons. Both are now re-scoped with `.tl-container` exceptions. Check the
canvases after touching any global selector in `index.css`.
</Callout>

Two consequences worth knowing before editing `App.tsx`:

- **`initMermaid()` lives inside the boundary.** It used to run at `App.tsx`
  module scope *and* from the theme effect, which is precisely what pinned
  mermaid into the entry chunk. It now runs from an effect inside
  `MermaidDiagram` keyed on `isDark`, so a theme switch still re-themes and
  re-renders every diagram on screen — without `App.tsx` holding a reference to
  mermaid.
- **Node/edge normalization moved to `FlowDiagram`.** It needs reactflow's
  `Position` enum, and that is a *value* import: pulling it into `App.tsx` alone
  would drag all of reactflow back into the entry chunk. `App.tsx` passes raw
  `diagramData` down and imports only the `DiagramData` **type**.

The full-screen editors split chrome from canvas: the modal header renders
eagerly so it opens instantly, and only the canvas inside it suspends.

### Every lazy canvas needs an error boundary, not just a fallback

`React.lazy` re-throws a failed `import()` **during render**. With only the
app-wide boundary in `index.tsx` above it, one un-fetchable chunk replaced the
entire viewer — sidebar, nav and the prose being read — with the full-screen
crash card. And it could not be dismissed: React caches the rejected promise on
the lazy component for the life of the page, so the crash card's *Try again*
re-threw the same error immediately.

`components/LazyCanvas.tsx` pairs the Suspense fallback with a local boundary so
the blast radius is one block. It offers **Reload the page**, which actually
recovers, rather than a retry that provably cannot.

Triggers are ordinary: a dev server restart, a deploy rotating content hashes
with a tab still open, a flaky connection mid-chunk.

<Callout type="warning">
Nothing fails if the splitting regresses. Add a static import of a heavy library
anywhere the entry can reach and the app still works, the types still check, the
other tests still pass — the bundle just quietly gets big again.
`code-splitting.test.ts` is the only thing standing there. It walks the eager
import graph from `index.tsx` rather than checking a hardcoded file list, and
understands the import forms that actually defeat splitting.

Its first version did neither, and review proved two ways straight past it by
building the mutated bundles: a bare `import 'tldraw';` (no `from`, so the regex
never matched) put the entry back to **1188 KiB**, and an `export { Position }
from 'reactflow'` in the unchecked `types.ts` put it back to **374 KiB** — both
while the test reported green. Treat that as the standing warning about
source-text gates: they are worth having, and they are only as good as the
grammar and the file set they cover.
</Callout>

The viewer has **no LLM dependency and no API key**. It previously shipped a `frontend/services/geminiService.ts` that called the Google Gemini API straight from the browser, with `vite.config.ts` inlining `GEMINI_API_KEY` into the bundle via `define` — for two methods nothing ever invoked. Both the service and the `define` block are gone; summarization and structure suggestion belong to Claude Code over MCP, which has the repo context this never did.

## Webfonts are self-hosted

`frontend/fonts/` holds eight `woff2` files (**349 KiB**), declared by
`styles/fonts.css` and imported eagerly from `index.css`. All four families are
**SIL OFL 1.1**; the licence text and the exact regeneration command are in
`frontend/fonts/README.md`. The OFL requires the licence to ship with the fonts,
so that file is not optional. They replace a
render-blocking `<link>` to `fonts.googleapis.com` plus two `preconnect`s — a
cross-origin stylesheet round-trip before first paint, then font files from a
second origin.

For a local-first tool that was a real gap: the viewer could not render its own
typography without the internet.

<Callout type="info">
**Self-hosting made the viewer *lighter*, not heavier**, because the fonts are
requested as variable **weight ranges** (`wght@400..700`) rather than the
discrete weights the old `<link>` asked for. One variable file per family per
subset covers every weight, so four static Inter instances collapse into one.

| | via Google Fonts | self-hosted |
|---|---|---|
| Classic, first view | 220 KiB | **31 KiB** |
| Atelier | 367 KiB | 130 KiB |
| third-party origins | 2 | **0** |

Mirroring the old discrete-weight request would instead have cost 1243 KiB on
disk. Measured, not estimated — `document.fonts` plus the resource timings.
</Callout>

`unicode-range` is copied verbatim from Google's own CSS, so the browser still
fetches only the subsets a page needs: an English doc pulls `inter-latin.woff2`
and nothing else, and `latin-ext` arrives only when accented characters do. Only
**latin + latin-ext** are vendored — Cyrillic, Greek and Vietnamese are not; add
them to `styles/fonts.css` if a corpus needs them. Fraunces and Hanken Grotesk
are Atelier-only and are never fetched in Classic.

<Callout type="info">
**`font-black` renders at 700, not 900 — and always has.** Inter is declared
`400 700`, matching the weights the old `<link>` requested, so a 900 request
clamps to the top of the axis (measured: identical glyph widths at 700 and 900,
no synthetic bolding). The eight `font-black` classes in `App.tsx` therefore
paint exactly what they painted before this change.

Do not "fix" that by widening the range to `100..900`. Inter's variable font
supports it, but the headings would get visibly heavier — a design change
dressed up as a font fix.
</Callout>

## Dev Server Port

The port is **not** hardcoded. `vite.config.ts` reads **`CATRYNA_VIEWER_PORT`** and falls back to **1307** when it is unset, non-numeric, or outside 1..65535 — the same rule as `viewerPort()` in `src/doctor.ts`.

It also sets **`strictPort: true`**, so a taken port is a hard startup failure instead of a silent bump to 1308. That is deliberate: `catryna doctor` advertises `http://localhost:<that port>` as the suite hub's `ui` URL, so a viewer that drifted to another port would make the advertised URL a lie. Keep the two parsers in lockstep.

## Main Components

**App.tsx** - Main application component with:

- Header status pill showing the **real** drift summary from `/api/drift` ("● 12 verified", amber with counts when anything is stale or broken). It was previously a hardcoded green "● Synced" backed by nothing.

- Version string injected from the repo root `package.json` at build time via a vite `define`. It was previously hardcoded `v2.5.0` while the package said `1.3.0`.

- Sidebar navigation with collapsible folder tree

- Project selector — lists every scanned project that has a `.docs/_index.json` and switches the server's docs root

- Command palette for quick doc search. It opens from the header **Search** button; the `⌘K` next to it is a rendered hint only — no keydown handler is registered.

- Document viewer with block rendering

- Table of contents (sticky sidebar) with an IntersectionObserver scroll spy

- Theme switching on two axes: a named **style** (`classic` / `atelier`) and a light/dark **mode** (see below)

- Settings modal for preferences, persisted to `localStorage` (`catryna.prefs.v1`). **Canvas Style** (`clean` / `sketchy`) only styles the whiteboard *placeholder card's* border in `BlockRenderer` — tldraw itself has never honoured it. `WhiteboardEditor` used to take the pref as a prop and ignore it; the dead prop is gone rather than left to imply an effect it does not have.

- Version history sidebar

- Toast notifications

## Theming

Two independent axes, and keeping them separate is what lets a second identity exist without a rewrite:

| Axis | Values | Applied as |
|---|---|---|
| **Style** (`themeStyle`) | `classic`, `atelier` | `<html data-theme="…">` |
| **Mode** (`theme`) | `light`, `dark`, `system` | `.dark` class on `<html>` |

**Classic** is the original Stripe-inspired look and honours the mode. **Atelier** is the [catrynawiki.com](https://catrynawiki.com) identity — `#0d0d16` canvas, the Turbo Flow gradient as signature, Fraunces display type over Hanken Grotesk, radial glows and film grain — and is **dark only**, so it pins the `dark` class and disables the mode control rather than hiding it.

<Callout type="info">
Atelier disables the mode buttons but deliberately does **not** reset the stored
`theme`, so `{themeStyle:'atelier', theme:'light'}` is a normal state to be in.
Anything deriving dark/light must therefore consult `themeStyle` too — deriving
it from `prefs.theme` alone is what themed diagrams against the wrong canvas.
See `styling/diagram-themes`.
</Callout>

**`system` tracks the system**, via `hooks/useSystemTheme.ts`. It previously
read `matchMedia(...).matches` once inside a memo keyed on the user's own
preferences, with no `change` listener anywhere in the app — so changing the OS
appearance did nothing until a reload. Worth knowing when testing it: DevTools
colour-scheme emulation changes what the query *matches* without dispatching
`change`, so a browser pass cannot exercise the listener. `useSystemTheme.test.tsx`
drives it with a stub that can.

### How a whole theme swaps without touching the components

Every palette colour is declared in `index.css`'s `@theme` block as `rgb(var(--c-name))` rather than a literal, and each theme defines that `--c-*` set further down the same file. A named theme therefore re-skins the entire app by swapping one block of variables — no edits to the hundreds of `dark:bg-zinc-900`-style classes across `App.tsx`. v4 composes opacity through `color-mix()`, so `bg-zinc-900/40` still yields a translucent *themed* colour.

Class-based dark mode comes from `@custom-variant dark (&:where(.dark, .dark *))`, since v4 defaults to `prefers-color-scheme`.

<Callout type="warning">
**`@source` is declared explicitly.** v4's automatic content detection produced **zero utilities** here — the compile succeeded and the theme variables were emitted, so every colour silently fell back to browser defaults instead of failing loudly. The explicit list also documents which files may contain class names.
</Callout>

<Callout type="warning">
**The theme is applied by a blocking inline script in `index.html`, before first paint** — and that is not only about avoiding a flash of Classic-light.

**"Lockstep" is a real requirement, and the two drifted.** The script treated a
**missing** `theme` key as `system`, while `App.tsx`'s defaults object says
`theme: 'dark'`. So every first-time visitor on a light-mode OS painted light
and then flipped to dark on mount — the exact flash the script exists to
prevent, on every new install, not just on a hand-edited prefs blob. The script
now reads a missing `theme` as dark. If you change the defaults in `App.tsx`,
change the script in the same commit.
 When `.dark` was added to `<html>` *after* paint, `<body>` was observed **not** to re-style for the descendant `dark:` selector: it matched `.dark\:bg-zinc-950:where(.dark, .dark *)` yet kept its `bg-white` background, while an identical `<div>` created afterwards resolved correctly. Setting the class before body is first styled removes the invalidation step entirely. Keep that script in lockstep with the theme effect in `App.tsx` and with `PREFS_KEY`.
</Callout>

`white` and `black` are deliberately **not** themed tokens: `bg-white` is a surface while `text-white` is ink on a coloured button, and one token cannot be both. No `.bg-white` override is needed either — all 25 uses are paired with a `dark:` variant and Atelier always runs dark, so the dark variant wins on its own. (An override did exist briefly; under the CDN, runtime-injected utilities landed *after* `index.css`, but with `@import "tailwindcss"` they now come *first*, so the override began beating `dark:bg-zinc-950` and lightened the canvas.)

Doc headings render as `<div>`s rather than `<h1>`/`<h2>`, so the reading styles hang off a `catryna-doc` container class on the doc column instead of element selectors.

## Key Features

### Block Renderer

Renders different block types with appropriate styling:

- **paragraph** - Text with a small inline-markdown parser (bold, italic, code, links)

- **heading-1 / heading-2 / heading-3** - H1 gets its own size; H2 and H3 currently share one style

- **code** - Read-only `<textarea>` with optional line numbers. There is no syntax highlighting, and the copy button only raises a "Copied" toast — it does not write to the clipboard.

- **callout** - Rendered with a single info style; `metadata.level` is not yet used to vary the colours

- **table** - Markdown or `<Table data={...} />` tables, from `metadata.headers` / `metadata.rows`

- **diagram** - Mermaid (rendered via the lazy `MermaidDiagram`, with an expand/zoom modal) when `metadata.diagramData.mermaid` is set, otherwise an interactive React Flow canvas (the lazy `FlowDiagram`). The expand modal clones the already-rendered container's `innerHTML`, so it costs no second load and has nothing to show until the lazy chunk has landed.

- **whiteboard** - A placeholder card that launches the full-screen tldraw editor. Stored `whiteboardData` is neither loaded into nor saved from the canvas.

### The trust surface is a set of PURE VIEWS

`components/Trust.tsx` holds `VerifiedBadge`, `DocTrust`, `StatCard`, `CoverageTrendChart` and `CoverageView`. None of them fetch; every one takes its data as props. `CoverageReport` in `App.tsx` is now four lines of hook wiring around `CoverageView`.

<Callout type="info">
This split is a **safeguard**, not tidiness. A component that fetches its own data can always be edited to skip the fetch and keep the number — which is exactly how an 84% health score, 42 pages and 12 missing items sat on this screen with no API behind them. A component that only *receives* data structurally cannot display something it was not given.
</Callout>

#### Visual weighting is deliberate — do not "fix" it

The status dot is **not** styled uniformly across states, and that asymmetry is the design:

| State | Treatment | Why |
|---|---|---|
| `clean` | recessed — dimmer and slightly smaller, dimmer still in the sidebar | In a healthy corpus nearly every row is clean. Fourteen identical dots is texture, not information. |
| `drifted` / `broken` | full opacity, soft halo, and a slow pulse | These are the rows that need a human. Motion should mean "look here". |

If every state pulsed, or every dot carried equal weight, the badge would stop
communicating — the same "if everything is marked, nothing is" failure the
`volatile-fact` lint rule was calibrated around. The pulse is additionally
disabled under `prefers-reduced-motion`.

`components/trust.test.tsx` renders these under happy-dom and asserts the property that would have caught the original bug: **with no data, no numbers.** A failed fetch must produce zero digits; a null drift status must produce no badge; an empty trend must explain itself rather than draw axis numbers. With real data, every digit on screen must trace to a prop. Mutation-checked by reintroducing the literal `84%` — the suite fails.

The DOM registration lives in `happydom.ts`, imported by the test rather than wired as a `bunfig.toml` preload: a preload only applies when `bun test` runs from that directory, and `bun run check` runs from the repo root. A gate that passes from only one directory is not a gate.

### Error Boundary

`components/ErrorBoundary.tsx` wraps the whole app in `index.tsx`. Without it, a single render-time throw unmounted the React root to a blank white page — no message, no indication the *viewer* had failed rather than the project being empty.

The hook-level normalizers are the real fix; this is the floor beneath them. It states plainly that `.docs/` is untouched, since nothing in the viewer writes.

It recovers by clearing the error state, so a transient failure does not require a reload.

<Callout type="info">
It was briefly written with hand-declared `props`/`state` and reload-only recovery, because the project had no `@types/react` and `React.Component`'s generics did not flow. Adding the types removed that constraint, so the workaround is gone.
</Callout>

### Preview Mode (formerly "Edit")

Content-editable blocks for previewing changes locally. **Nothing persists, and the UI now says so** — a banner names the `.mdx` file to edit and the `update_doc` MCP tool.

<Callout type="warning">
This used to present a **Save** button that ran an 800 ms timer and toasted "Saved". There was no write path (the docs API is `GET`-only), and the contentEditable blocks are never read back into state — the edits existed only as DOM nodes and were discarded on the next render. Nothing was saved, nothing could have been, and the user was told otherwise.
</Callout>

A real write path is deliberately not built yet. `updateDoc` re-serializes blocks through the simplified parser — the documented lossy round-trip that mangled rich MDX and left orphaned closing callout tags earlier in this project's history. Viewer-side writes on top of that would corrupt docs; the honest read-only failure mode is better than the silent destructive one. Fixing the serializer is the prerequisite.

### Version History

The sidebar renders `currentDoc.history`, but the API never returns a `history` field and `toDocument()` never sets one — so it always shows "No versions found", and **Revert** only closes the panel. Git is the real history today.

### Coverage Report

Real data, fetched from `GET /api/coverage` by the `useCoverage()` hook. Shows coverage percent, doc counts, a doc-trust breakdown from `GET /api/drift`, a broken-anchors panel, and the undocumented-module list.

On fetch failure it renders "Coverage unavailable" rather than numbers — the screen never invents a figure it could not compute.

<Callout type="info">
This screen previously displayed **hardcoded placeholders**: an 84% health score, 42 pages, 12 missing, and four filenames that did not exist in the repo, with no API call behind it. It was reachable from the UI and read as a genuine report. Fixed in Phase 2 by extracting `src/coverage.ts` and adding the endpoint.
</Callout>

The header previously carried an **Auto-Generate Missing** button; it was scaffolding for the removed Gemini integration and never had a handler. Removed rather than left as a dead control.

### Coverage Over Time

`CoverageTrendChart` renders coverage across git history as inline SVG — no chart library, since this view is its only consumer.

Two deliberate choices worth keeping:

- The **y-axis is pinned to 0–100**, not fitted to the data. An auto-scaled axis turns a 2-point wobble into a visual collapse, and this chart exists to show whether documentation is keeping pace, not to dramatize noise.
- The **x-axis is scaled by timestamp**, not by commit index. It previously spaced points evenly by index while labelling the axis with dates — on this repo a six-month gap and a 90-second gap rendered as identical widths, so "when did our docs fall behind?" was answered off the wrong part of the chart. Same defect class as the hardcoded 84%: a plausible picture that isn't true.
- The **largest single drop is marked**, because the actionable question is not "what is coverage" but "when did it fall, and to what". When the series is downsampled it reports a *range* (`between <sha> and <sha>`) rather than naming one commit, since consecutive samples can skip many commits and blaming the later endpoint is a false attribution. Every point carries a tooltip with commit, date, percent, modules, and doc count.

`sampled N of M commits` appears whenever the series is a selection, so the chart never implies it plotted every commit.

<Callout type="info">
This is the slowest panel on the dashboard — two git reads per sample — so it has its own loading state. Without one the section sat blank while the rest of the page was populated, which reads as "no data" rather than "still working".
</Callout>

### Verified Badge

Per-doc drift status (PRODUCT_ROADMAP Phase 2), from `GET /api/drift` via `useDrift()`:

- 🟢 **Verified** — clean at HEAD
- 🟡 **Stale** — anchored code changed since verification
- 🔴 **Broken** — an anchored file no longer exists
- ⚪ **Unverified** — no baseline, never checked

Rendered as a compact dot per file in the sidebar (`SidebarItem`) and as a `DocTrust` line under the document title, which also names the baseline commit and the changed files — a badge says a doc is stale, the file list says what to go re-read.

Switching projects refetches drift. Drift is keyed by doc **path**, and paths collide across projects (`architecture/overview`, `getting-started` are near-universal), so without the refetch the previous repo's verdicts stayed on screen — an unverified doc in the new project rendered a green "Verified" dot with a baseline SHA from a different repository.

<Callout type="info">
The badge renders **only when there is a verdict**. A doc with no anchors, or a viewer that could not reach `/api/drift`, shows no dot rather than a green one: failing to ask is not a clean bill of health. This mirrors the `unanchored` / `unknown` states in `src/freshness.ts`.
</Callout>

The status is **not** derived from frontmatter. A doc's stored `verifiedCommit` records which commit it was checked at, never whether the code has moved on since — only the git-backed engine can answer that.

### Diagram/Whiteboard Editors

Full-screen modal editors for visual content:

- **DiagramEditor** - React Flow canvas with controls and minimap

- **WhiteboardEditor** - full-screen tldraw canvas

Both are **scratchpads, and now say so.** Each shipped a prominent accent
**Save Diagram** / **Save** button whose entire handler was `onClose` — so the
control most likely to be pressed after rearranging nodes was the one that threw
the work away. Same defect as the removed Preview-mode Save, and for the same
reason: the docs API is `GET`-only and `updateDoc` still round-trips through the
lossy parser, so a real write path here would corrupt docs rather than persist
them. Both now carry a labelled **Close** and a `ScratchpadNotice` banner naming
the `.mdx` file and the `update_doc` tool.

Connection handles are switched off in both canvases (`nodesConnectable={false}`).
There is no `onConnect` handler and nowhere to persist an edge, so dragging from
a handle drew a line that vanished on release. reactflow defaults that prop to
**true**, so the read-only in-doc canvas was advertising it too. Nodes stay
draggable — nudging one to read an overlapped label is useful and harmless.

Switching it off correctly takes three pieces, and the first two were missed on
the first attempt:

- **Custom node types must forward `isConnectable`.** reactflow resolves the
  canvas-level flag and passes it to each node as a **prop**; `Handle` does not
  read it from the store and defaults to `true`. `TurboNode` took only `data`,
  so on a turbo-typed diagram the handles stayed fully live — crosshair cursor,
  `pointer-events: all`, click-connect latching — while the connection *line*
  was suppressed, because that part does read the store. Strictly worse than
  leaving connections on. Measured on a turbo diagram: 4/4 handles `connectable`
  + `connectionindicator` before, 0/4 after.
- **The editor's `<Controls>` lock had to go** (`showInteractive={false}`). Its
  handler writes `nodesDraggable`/`nodesConnectable`/`elementsSelectable`
  straight into the store, and reactflow only re-syncs a prop into the store
  when the prop's *value* changes. Ours is a constant `false`, so one
  lock/unlock round-trip turned connections back on permanently.
- **A non-connectable handle is still painted.** reactflow only makes it inert;
  `index.css` hides it (`.react-flow__handle:not(.connectable)`), so the dot
  that reads as "drag from here" is not there to be believed.

<Callout type="info">
The first attempt passed a browser check because the only React Flow diagram in
this repo uses `input`/`output`/default nodes — and the **built-ins** forward
`isConnectable` correctly. The custom `turbo` type is the one that did not. A
visual pass over the corpus you happen to have is not coverage of the code path.
</Callout>

Both keep their **chrome eager and their canvas lazy**, so the modal opens
immediately and the canvas fills in behind a spinner rather than the click
appearing to do nothing while a megabyte downloads. The editable canvas
(`FlowEditorCanvas`) also owns its own node/edge state.

## Data Fetching

Uses custom hooks in `hooks/useDocs.ts`:

- `useDocsList()` - Fetches all docs from /api/docs

- `useDoc(path)` - Fetches single doc from /api/docs/{path}

- `useDocsSearch()` - Search with /api/docs/search?q=...

The project list is fetched directly in `App.tsx` (no hook): `GET /api/projects` on mount, and `POST /api/projects/select` to switch.

## The Docs API

Nothing is proxied. The request handling lives in **`frontend/docs-api.ts`** (`createDocsApi({docsRoot, findProjects})`), and `vite.config.ts` only decides the on-disk wiring and registers the middlewares. The split exists so the API can be tested without booting a dev server — it previously had **no automated coverage at all**, including the two security fixes below. `docs-api.test.ts` now carries a dedicated suite, with the traversal and allowlist cases mutation-checked against reverted-vulnerable versions.

The endpoints read the `.docs/` folder off disk:

- `GET /api/docs` - returns `_index.json` verbatim

- `GET /api/docs/search?q=` - substring match over title, tags, and path; capped at 20 results

- `GET /api/docs/:path` - reads `{path}.mdx`, runs the config's own `parseMdx()`, and returns `{ ...indexMetadata, path, blocks, raw }`

- `GET /api/projects` / `POST /api/projects/select` - project discovery and switching

- `GET /api/coverage` - real coverage, via `computeCoverage()` from `src/coverage.ts`

- `GET /api/drift` - per-doc drift status keyed by path, via `computeDrift()` from `src/drift.ts`, for the verified badge

- `GET /api/coverage/trend?points=N` - coverage over time, via `computeCoverageTrend()` from `src/trend.ts` (default 40 points, capped at 200)

Any other `/api/projects/*` URL returns 404. Falling through without `next()` or `res.end()` previously left the socket open forever — a `GET` to `/api/projects/select` hung until timeout, and a handful exhausted the browser's per-origin connection pool.

<Callout type="warning">
**Security, both found in adversarial review and verified exploitable against a running dev server.** These matter more than "it's only a dev server" suggests, because `server.host` is `0.0.0.0` — every device on the same network can reach it unauthenticated.

- `GET /api/docs/:path` joined the request path onto `docsRoot` with no containment check, serving **any `.mdx` file on the machine** with its body in `raw`. It now strips query/fragment, decodes percent-escapes *before* checking (so `%2e%2e` cannot smuggle a traversal), resolves, and requires the result to stay inside `docsRoot`.
- `POST /api/projects/select` accepted **any path on disk**, and because the handler `JSON.parse`s regardless of `Content-Type` it is a CORS *simple* request with no preflight — any page the developer visited could silently repoint the viewer with a `no-cors` fetch. `docsRoot` also becomes the cwd for git subprocesses. Selection is now restricted to the set `findProjects()` discovered.
</Callout>

The last two compute against the **project root** (the parent of the docs root), not the dev server's cwd — which is `frontend/`. They read `docsRoot` per request rather than capturing it, because `POST /api/projects/select` switches it at runtime. `/api/drift` passes `emit: false`: rendering a badge must not write to the suite event spine.

<Callout type="warning">
Because the Vite plugin imports the drift engine, `src/drift.ts` runs in a module context with **no `Bun` global**. `runGit` originally called `Bun.spawn` unconditionally; since every git failure in that engine degrades quietly by design, it did not throw — it reported a real git repository as "not a git repository" and would have rendered every doc unverified. Both `runGit` and `runHayven` now feature-detect through `globalThis` and fall back to `node:child_process`.
</Callout>

Because it hangs off `configureServer`, the API exists **only in `vite dev`** — a `vite build` bundle has no backend. The docs root defaults to `../.docs` and can be overridden with `DOCS_ROOT`; project scanning honours `PROJECTS_ROOT` before falling back to sibling and common dev directories.

<Callout type="info">
`parseMdx()` here is a second, independent parser — separate from `src/storage.ts`. It keeps only the `blocks` it produces; the frontmatter it parses is discarded, and the metadata the viewer shows comes from `_index.json`. Frontmatter arrays are written as JSON (so values containing commas or quotes round-trip), and this parser `JSON.parse`s any value starting with `[` — after a legacy `'` → `"` substitution that can corrupt an apostrophe inside an otherwise valid JSON string.
</Callout>
